## 3. Duplicates and HF↔GCS overlap — uniform-mirror policy (proposed)

Sha-identical duplicates found:
- eft31b-submission (both copies): each `adapter/` dir duplicates its `adapter/checkpoint-N/` (same
  lfs sha). Upload once, GCS server-side copy for the twin path. Saves ~12 GB of streaming.
- arcadia↔jbostock `dose_rows_v2/rows{256,512}`: identical shas → one migrated artifact, receipt
  records both HF sources.
- No other cross-repo big-file sha dups exist.

HF artifacts whose bytes very likely already sit on GCS old-layout (no common hash exists across
HF-sha256 / GCS-md5 to prove it cheaply): gemma3 `mixed_4ep_prop/sft/end` (12B+27B, ~84 GB), run-4
sampler adapter (2 GB), runBv2 trainer checkpoints (~24 GB).
**Proposal:** apply one uniform rule — every weight byte that is on HF streams into
`python4-weights/` with full verification, old-layout GCS copies untouched. Cost of the ~110 GB
double-store ≈ $2/mo; benefit: self-contained receipts, no reliance on unverifiable cross-system
equality, and deletion gates that depend only on our own verified copies. (Q5)

## 6. Phase 3 mechanics (copy + verify) — after ack only

Per artifact, per file (largest single file 4.9 GB; disk cap ~10 GB, far under the 50 GB limit):
1. `hf_hub_download` at the **pinned revision** (`HF_HUB_DISABLE_XET=1`) to `/workspace/…/scratch/`.
2. `sha256sum` locally → must equal the HF LFS sha256 from the inventory (non-LFS small files:
   recorded as computed).
3. `rclone copyto` to the target path (rclone verifies GCS md5 end-to-end on upload); then remote
   size re-check via `rclone lsjson`; delete local file.
4. Dedup twins: `rclone copyto gcs:… gcs:…` server-side, then size check.
Verification triple = HF LFS sha (source of truth) ⇔ local sha256 ⇔ rclone md5-verified upload +
remote size. Failures are loud: any mismatch aborts the artifact, partial uploads are deleted.
- Per-artifact receipt JSON → `gs://…/python4-weights/<artifact>/…/_receipt.json` AND mirrored to
  `receipts/` here (committed): source repo+revision, file list with sizes+shas, GCS paths, UTC
  timestamp. Marker `_MIGRATION_COMPLETE` written **only after** every file of the artifact
  verifies (marker-last).
- Repo-level README/.gitattributes archived to `gs://…/python4-weights/_hf_repo_meta/<repo>/` and
  embedded in receipts (they die with tombstoning otherwise).
- Progress → `transfer.log` in this dir (not stdout); resumable: a re-run skips artifacts whose
  `_MIGRATION_COMPLETE` verifies.
- First artifact doubles as a throughput calibration: at 50/100/200 MB/s sustained, 1,768.6 GB ≈
  9.8/4.9/2.5 h streaming; budget 8–24 h wallclock incl. hashing. Runs `run_in_background` on this
  box (network+sha are cheap on 2 vCPU; API-box-appropriate).
- Storage delta: +1.79 TB on GCS ≈ **~$36/mo** (standard class). HF frees the same (2 repos are
  >0.5 TB public).

## 7. Phase 4 (tombstone + delete) — gated on coordinator ack of receipts

Per migrated repo, only after its receipts are acked: (1) commit a tombstone README.md (what lived
here, target GCS prefixes, migration date, receipt pointer, pinned pre-deletion revision);
(2) delete the migrated weight files from the repo (thinking-grpo-logs: weights only, logs remain);
(3) **Q6:** optionally `super_squash_history` so HF actually reclaims LFS storage — without it the
bytes stay retrievable via old revisions; with it, revision-pinned URLs (incl. those in our own
receipts) stop resolving. Recommendation: squash, since GCS+receipts become the record.
Never delete before the artifact's receipt is verified AND acked. Dataset repos untouched.
