## Part 1 — Current state of the code

### The map

The repo has three layers:

1. **`src/scimt/` — the shared library (~4.3k lines).** Small, deliberately
   pure/lazy-importing modules: the seed-matched install-match core
   (`match.py`), LoRA weight-noise perturbation (`perturb.py`), residual-stream
   activation noise (`act_noise.py`), the 4-axis robustness-profile reduction
   (`robust/profile.py`, `robust/pressure.py`), Tinker unlearning primitives —
   signed mean-normalized datums for SFT/gradient-ascent/GradDiff
   (`unlearn/core.py`) — plus corrective/DPO dataset generators
   (`unlearn/aligne_chain.py`), judge-free evals (`eval/`: belief probes,
   Tinker sampling, forced-choice value preference, MMLU+GSM8K capability), and
   response classifiers (`analysis/`).

2. **`experiments/msm_fig2_repro/repro/` — the de-facto value-eval core.**
   `data.py` / `evaluate.py` / `config.py` hold the corpora loaders, the
   forced-choice prompt templates, the lenient parsers + echo guard, and the
   logprob forced-choice scorer (with stance-meaning scoring to cancel the
   P('A')>P('B') letter bias). Everything value-flavoured downstream reuses
   these via `sys.path` insertion.

3. **Two training substrates**, used by different experiments:
   - **Tinker API path** (Qwen3-30B-A3B-Instruct, LoRA r32): training through
     the `aligne-sft` / `aligne-dpo` CLIs, chained via `--load-checkpoint-path`
     (state path) + a fresh `--out` per step. Used by `value_msm_install`,
     `msm_em_interaction`, `adversarial_finetuning`, `depth_suite`.
   - **RunPod/Unsloth path** (Qwen3-14B base+instruct, LoRA r64 merged to
     fp16): pod-side `train.py` / `value_eval.py` (vLLM) / `delta_apply.py`
     (task arithmetic), driven from a laptop by `msm_stage_comparison/run_plan.py`
     over **bellhop**, with GCS persist/restore of named checkpoints. Used by
     `msm_stage_comparison` and `lora_artifact_robustness`.

**Crucial context the doc doesn't reflect:** two of the doc's experiments
already have preliminary results in this repo:

- **Exp #2 (stage-of-post-training)** = `experiments/msm_stage_comparison/`
  (spec + full seed-0 phase-1 run + report, PR #140). Headline: **late-stage
  MSM (on the finished instruct model) generalizes as well or better than
  early/base-model MSM; interleaving alignment data into instruct training is
  the *worst* placement.** Phase 2 (unlearning durability) is pre-registered,
  its gate has passed, and it has *not* been run.
- **Exp #4 (MSM → misalignment FT vs classic EM)** = `experiments/msm_em_interaction/`
  (2 seeds, report, PR #137). Headline: **spec doc-SFT is inert w.r.t. EM, but
  the demonstration-style alignment-FT stage *amplifies* subsequent EM
  generalization** (~0.31 → ~0.44–0.47 OOD hit-rate at matched ID misalignment).

### Overall assessment

The code is **good — better than typical research code — and worth building
on.** Specific strengths I verified rather than took on faith:

- **Experimental discipline is encoded, not aspirational**: matched controls
  per arm (never "vs the off-the-shelf instruct model"), pre-registered
  hypotheses/gates in specs, confound endpoints ("how much does *just* MSM
  move the metric"), on-distribution NLL matching before OOD gaps are read,
  capability guards (MMLU/GSM8K) at every endpoint, seeds threaded end-to-end,
  and raw responses persisted separately from classification so metrics can be
  recomputed without re-spending compute.
- **Judge-free headline metrics** wherever possible (forced-choice string
  match + logprob fallback; exact-match capability grading), with the LLM
  judge confined to the EM eval where it's unavoidable.
- **Idempotency/resume discipline everywhere**: GCS resume-or-train in
  `run_plan.py`, per-(ckpt,scale,seed) response caches in `act_noise.py`,
  checkpoint-reuse in `train_stages.py`, judge caches in `eval_em.py`.
- **Hard-won gotchas are captured in code + comments**, e.g.: the Tinker
  cookbook silently auto-resumes if you reuse `--out` (so chains use fresh out
  dirs); training chains must load the *state* path while sampling uses the
  *sampler* path; `reduction="mean"` would silently undo gradient ascent (hence
  hand mean-normalization in `unlearn/core.py`); vLLM teardown SIGABRTs after
  results are safe (hence write-then-`os._exit(0)` and judging eval ops by
  artifact, not exit code); GPU-process scrubbing between pod ops; EOS-token
  stripping before the echo guard (`classify_value.py`); the gated-Llama
  fallback. Losing these by rewriting from scratch would be expensive.
- **153/160 unit tests pass** on a clean machine with only
  `pytest,httpx,torch,safetensors` installed (the pure cores really are pure).

The problems are concentrated in **portability/environment assumptions**
(the code currently only runs on the author's machine), a handful of **metric
edge cases**, and some **stale tests**.

#### P1 — correctness & consistency, before producing new numbers

4. **Fix the 7 stale failing tests.** `tests/test_{ed,qe,us}_gate.py`,
   `test_match_sweep.py`, `test_qe_benign_ft.py`, `test_consolidate.py` still
   assert the old ε-gated `MatchResult` schema that PR #107 deliberately
   removed from `depth_suite/match_sweep.py` ("B recorded, not gated"). Update
   or delete them — a red suite at HEAD hides real regressions.
5. **Standardize the B denominator across scoring paths.** Three subtly
   different conventions coexist:
   `value_pref_rate_logprob_async` returns `n_aligned / n_valid`
   (`value_pref.py:204`); `classify_value.aggregate` and
   `msm_stage_comparison/scoring.py` return `n_aligned / n` (invalid counts as
   not-aligned). They agree only when `valid_rate == 1`. Pick one headline
   convention (I'd take `n_aligned / n` + always reporting `valid_rate`, which
   hybrid mode effectively guarantees anyway) and make the logprob path match.
6. **Chat-template portability (prerequisite for exp #1 and any non-Qwen
   run).** `scimt/eval/sample.py:47`, `act_noise.py:43`, and
   `value_pref.py:186` hardcode the Qwen ChatML string
   (`<|im_start|>user\n…`). `get_decoder_layers` (`act_noise.py:69`) assumes
   `model.model.layers`. Parametrize prompt-wrapping by tokenizer/renderer
   (the pod-side code already does this correctly via
   `tok.apply_chat_template` + a ChatML fallback) and make the layer accessor
   configurable. Also sweep the pinned model constants
   (`capability.MODEL`, `unlearn.core.DEFAULT_MODEL`, `value_pref.MODEL`) into
   per-call parameters with defaults.
7. **MMLU grader false-positives on the article "a".**
   `capability.grade_mmlu` matches the first standalone `[A-D]` letter
   case-insensitively, so a rambling response ("As a language model …") grades
   as answer "A". Fine for temp-0 well-behaved models; systematically biased
   for the degraded/noised models this grader is specifically used to guard.
   Cheap fix: require uppercase or an anchored `Answer: X` / leading-letter
   form before falling back.
8. **Loss-masking convention differs between the two training substrates.**
   The Tinker path trains on assistant tokens only
   (`TrainOnWhat.LAST_ASSISTANT_MESSAGE` in `unlearn/core.py`; aligne-sft
   renderer-based), while the pod Unsloth path (`pod/train.py`) trains on the
   **full rendered sequence including user turns** (plain `SFTTrainer`, no
   completion masking). Internally consistent within each experiment (arms and
   controls share the recipe), but a cross-substrate comparability gotcha and
   a deviation from standard chat-SFT practice. Decide + document; if we keep
   full-sequence on the pod path, say so in specs.
9. **De-duplicate the forced-choice/logprob scorer.** It exists three times
   (`repro/evaluate.py`, `msm_stage_comparison/pod/value_eval.py`,
   `scimt/eval/value_pref.py`) — partly justified (the pod copy can't import
   scimt), but drift is a real risk since exp #1/#3/#7 will all touch it.
   Either consolidate into `scimt` with a "copy to pod" staging step, or add a
   parity test pinning the three implementations to identical outputs on a
   fixture.

#### P2 — hygiene / nice-to-have

10. **Module-name collision hazard:** the repro's flat modules are named
    `evaluate.py`, `data.py`, `config.py` and are imported by bare name after
    `sys.path.insert(0, ...)`. `evaluate` collides with HF's `evaluate`
    package, `data`/`config` with anything. `insert(0)` currently wins, but
    this will eventually bite (e.g. pytest collection or an import that
    happens before the insert). Renaming to `fig2_{data,evaluate,config}.py`
    is cheap now, painful later.
11. **Unbounded judge concurrency** in `msm_em_interaction/eval_em.py`
    (`asyncio.gather` over ~200 judge calls with no semaphore) — works until
    it rate-limits; add a bound like the samplers have.
12. **Clustered-sample statistics in the EM eval:** the Wilson CI treats
    8 questions × 25 samples as n=200 independent draws; samples within a
    question are correlated (the per-question hit-rates in the report confirm
    it). CIs are anti-conservative. Note it, or bootstrap over questions.
13. **`stage_data.py` prints row counts by re-reading the file it just wrote**
    (harmless), and `smoke` payload naming (`eval_payload_smoke.json` vs
    `payload_smoke.json` in the help string) is inconsistent — trivia, fix
    when touched.

## Part 2 — The experiments in the doc

### Framing

The doc's quick list, annotated with what already exists:

| # | Experiment | Status in repo | Infra fit |
|---|---|---|---|
| 1 | MSM across model sizes/families | not started | pod harness reusable; blocked on P1-6 (templates); corpora are model-agnostic |
| 2 | MSM at different post-training stages | **phase 1 done (seed 0)**; phase 2 (unlearning) pre-registered + gated-open | everything exists; checkpoints persisted to GCS |
| 3 | MSM × SFT- vs RL-alignment | not started | SFT + DPO exist (aligne); **no RL trainer anywhere** |
| 4 | MSM → misalignment FT vs EM | **done (2 seeds, report)**; follow-ups identified | full harness exists |
| 5 | MSM × reasoning models | not started | substrate pins thinking OFF everywhere; needs renderer/eval work |
| 6 | Traits in tension | not started | needs corpus generation + a judge-based rubric (new) |
| 7 | Framing of MSM docs | not started | needs doc-*generation* pipeline (aligne synthdoc); eval side exists |
| 8 | MSM one way, RL the other | not started | subsumed by #3+#4 (see below) |
| 9 | Agentic long-trajectory evals | not started | no agentic eval infra in repo at all |

### What I'd do first (recommended order)

1. **Exp #2 phase 2 — unlearning durability across stage arms.** Highest
   information per dollar and effectively pre-paid: pre-registered in
   `msm_stage_comparison/spec.md`, its gate has passed, and all 8 arm + 3
   control checkpoints are persisted. It also directly tests the doc's central
   intuition — phase 1 showed late-stage MSM *generalizes* fine, but the
   "fine-tuning at the end bakes in shallow behaviour" claim is really about
   **durability**, which phase 1 explicitly could not measure (report caveat
   3). If late-stage MSM generalizes well *and* unlearns cheaply, that
   reconciles the phase-1 result with the intuition; if it's also durable, the
   intuition is just wrong for MSM. Either answer reshapes experiments #1–#7.
   *Prerequisite: GCS read access to the author's checkpoint prefix (P0-2).*
2. **Confirmation seeds for the two headline results.** Both existing reports
   are seed-limited (exp #2: seed 0 only; the affordability ordering is ~2 SEM;
   exp #4: 2 seeds). The spec already gates this (+2 seeds on the extreme
   pair). Cheap, mechanical, and we shouldn't build a research program on
   unconfirmed seed-0 contrasts.
3. **Independent replications of exp #2 and exp #4 — different value target
   and different model.** Seeds test noise; they don't test whether the result
   is an artifact of the setting (Qwen substrate, chloeli corpora/evals,
   specific value pair). Since the stage-comparison and EM-interaction
   findings will steer everything downstream, replicate each once with the
   substrate and target swapped before leaning on them:
   - **Exp #2 replication:** rerun the stage arms on a second family
     (Llama-3.1-8B is the natural choice — connects to the original paper) and
     ideally a third value from the #7 doc-gen pipeline. Design note: this
     *is* a large chunk of exp #1 (cross-family) — plan them as one grid so
     the replication cells double as exp-#1 cells rather than being paid for
     twice.
   - **Exp #4 replication:** different EM dataset (e.g. insecure-code instead
     of medical), a second judge for the same responses (judge-artifact
     check), and — per the report's own caveat — a spec corpus installing
     values the model does *not* already hold, plus the base-model-MSM
     variant.
   - Where cheap, also replicate the *analysis* path independently: recompute
     headline metrics from the persisted raw rows with fresh scoring code (or
     at least a second implementation of the parser) to catch metric bugs of
     the kind flagged in P1-5/P1-7.
4. **Exp #7 — framing of MSM docs.** Cheap on the eval side (identical
   pipeline to `value_msm_install` / stage comparison; only the corpus
   changes) and mechanistically the most informative next dial: exp #4 already
   suggests the doc-SFT stage is *not* where the generalization prior comes
   from, and framing ("[model-name] does X because Y" vs "[everyone] does X
   because Y") is the sharpest probe of whether self-reference matters. **The
   new work is corpus generation** — the repo has so far only *reused*
   chloeli's released corpora and has no validated in-repo MSM doc-gen recipe.
   `aligne-synthdoc` exists for exactly this; budget a validation pass
   (doc quality, token counts matched across framings, install gate à la
   `value_msm_install`) before the comparison. This pipeline is then reusable
   for #6 and for the exp-#4 follow-up (a spec corpus installing values the
   model does *not* already hold — the report flags that the philosophy-spec
   corpus partly re-installs Qwen's existing values, which may have muted the
   `msm_em` contrast).
5. **Exp #3 — SFT vs preference-based alignment, staged.** Do it as
   **SFT vs DPO first**: `aligne-dpo` + the labeled-comparison generators in
   `scimt/unlearn/aligne_chain.py` already exist, so "MSM → SFT-AFT" vs
   "MSM → DPO-AFT" at matched on-distribution alignment is runnable now and
   captures much of the SFT-vs-preference-learning question. Genuine online RL
   (RLHF/GRPO-style) is a new infra investment (Tinker cookbook has RL
   machinery, but nothing in this repo or aligne wraps it) — decide after the
   DPO result whether it's worth it. One design warning: the doc's "match
   on-distribution alignment" is essential and *harder* here than in exp #2 —
   NLL-matching doesn't transfer across objectives (DPO/RL don't optimize NLL),
   so matching needs a behavioral on-distribution metric instead. Spec this
   before running.
6. **Exp #1 — across sizes/families, but reframed (see red flags).** After
   the P1-6 template refactor. Use the **A2 recipe (MSM on the instruct
   model)** that exp #2 just licensed — that turns "very costly" into roughly
   a GPU-day per model: MSM + AFT + control-AFT + evals, no full instruct
   retraining. Sensible grid: Qwen3 {1.7B, 14B, 32B} × one other family
   (Llama-3.1-8B connects directly to the paper) × both values. Keep one
   full-pipeline (A3.5-style) replication at one non-Qwen model as an anchor.
7. **Exp #4 follow-ups** (base-model-MSM × EM; AFT dose-response; non-self
   spec corpus) — the existing result (alignment-FT *amplifies* EM
   generalization) is the most safety-relevant finding in the repo and is
   worth hardening: it's currently 2 seeds, one EM dataset (medical), one
   judge. Slot these behind #3 or interleave when Tinker capacity is idle.
8. **Exp #5 — reasoning models.** Doable *now* in its cheap form thanks to the
   exp-#2 result: MSM the reasoning-mode instruct model directly (A2 recipe)
   instead of the "obscenely expensive" base-model + full reasoning
   post-training route the doc worries about. The doc's confound concern
   (MSM-on-instruct being unclean) is *empirically* addressed by phase 1 for
   non-reasoning models — worth saying explicitly when we write this up. Real
   costs: renderer/eval changes (thinking ON changes the eval token budget,
   the forced-choice parsers must skip `<think>` blocks, and "where does the
   value show up — CoT or answer?" becomes a first-class measurement, which is
   arguably the interesting part). Medium effort, do after #1's refactor.
9. **Exp #6 — traits in tension.** Interesting and closest to "what will
   actually go wrong with spec training", but the most design-heavy: it needs
   (a) the doc-gen pipeline from #7, (b) a defensible rubric for the "hidden
   ideal behaviour" in tension cases — which is an LLM-judge metric, breaking
   the repo's judge-free discipline, and the doc itself flags rubric
   difficulty — and (c) 6+ arms with per-trait on-distribution matching.
   Write a spec + run a 2-arm pilot before committing to the full grid.
   Don't start until #7's pipeline exists.

### Not worth doing (as specced), and why

- **Exp #8 (MSM one direction, then RL the other; "maybe thrashing")** — as
  written it's exp #4 with RL in place of SFT, plus an unoperationalized
  "thrashing" observable. Fold it into #3/#4: once #3's RL (or DPO) arm
  exists, "train against the MSM direction" is one extra cell, and exp #4
  already defines the right measurement protocol (matched ID damage → OOD
  breadth). As a standalone experiment it has no defined metric and would
  duplicate infra.
- **Exp #9 (agentic long-trajectory evals) — defer, and don't build it
  ourselves.** It's an eval-development project, not an experiment: the repo
  has zero agentic infra, the metrics are judge-heavy and noisy, and every
  upstream question (which MSM recipe? which stage? does it survive
  post-training?) is still open. When the stack stabilizes, adopt an external
  agentic-misalignment suite rather than writing one; treat it as the capstone
  "does any of this matter in realistic settings" check.
- **Exp #1 at "very costly" full-pipeline scale** — the full base-model
  fine-tuning variant the doc costs as "Very" is dominated by the A2-recipe
  sweep above. One full-pipeline anchor point is enough; spending the
  difference on seeds and a second family buys strictly more inference.

### Red flags & general notes on the doc

1. **The doc predates the repo's own results, and two of its premises are now
   empirically challenged.** The "General thoughts" section asserts that
   fine-tuning at the end bakes in shallow behaviour while training throughout
   instils it more thoroughly — exp #2 phase 1 found the *opposite* ordering
   for generalization (late MSM best, interleaving worst), and exp #4 found
   the doc-SFT stage inert for EM interaction. Neither is fatal (durability is
   untested — hence phase 2 first), but the doc should be revised against
   these results so we don't design experiments around a prior the repo has
   already spent money disconfirming.
2. **"OOD-generalisation-gap" needs per-family matched controls in exp #1.**
   Base rates on the forced-choice evals differ across families/sizes
   (Qwen3-14B raw-base pro-America was 0.25), so raw gaps aren't comparable
   across models. The stage-comparison's matched-control discipline handles
   this — keep it, and report control base rates alongside gaps. Also expect
   floor/ceiling compression at small scales.
3. **Reasoning-first ambition vs thinking-off substrate.** The doc's opening
   says alignment research should target reasoning models, but every current
   pipeline pins thinking OFF (renderer, eval prompts, budgets). That's the
   right pragmatic choice so far, but it means #5 is not an incremental
   experiment — it's a substrate migration. Budget it as such rather than
   treating it as one more cell.
4. **Value/eval saturation risk when reusing the chloeli settings.** The
   pro-America/pro-affordability settings are validated and cheap, but A2 on
   pro-America already hits +0.38; ceiling effects will mask differences in
   follow-on comparisons (#3, #7). For fine-grained comparisons, prefer the
   affordability setting (more headroom) or bring a third value online via
   the #7 doc-gen pipeline.
5. **Several experiments (#3, #6, #7) hinge on "matched on-distribution
   performance", which is currently only operationalized for chat-SFT (NLL
   within ε).** Extending matching across objectives (DPO/RL) and across
   traits (#6) is design work that should be pre-registered per experiment,
   like the stage-comparison spec did — this is exactly the kind of detail
   the doc's "What would we measure?" sections currently leave open.
6. **Cost estimates in the doc look right in relative terms but the absolute
   picture changed:** exp #2's full seed-0 phase 1 came in around ~$200 of
   B200 time. The doc's "Very costly" for #1 assumed the full pipeline; with
   the A2 recipe, #1 is a mid-cost experiment. The genuinely expensive items
   on the list are now #5 (if done as substrate migration) and #6 (design +
   judge costs), not #1.
7. **Keep the robustness/durability battery as a standard endpoint panel.**
   The repo's distinctive asset relative to the MSM paper is the
   inductive-bias/durability toolkit (noise curves, cost-to-τ unlearning,
   benign-drift; `scimt.robust`, `scimt.perturb`, `scimt.unlearn`). The doc's
   experiments mostly measure OOD lift only. Attaching the cheap durability
   axes to every new MSM endpoint (they're mostly evals on existing
   checkpoints) differentiates the work and guards against the
   "generalizes-but-shallow" failure mode that phase 1 couldn't see.
